# UI Runtime Data Map

## Bottom Line

`agent_runtime` UI Console must read the runtime as source of truth and treat
the browser as a control surface only. The first UI adapter should be read-first:
derive normalized view records from existing task files, backlog board, message
files, session records, event logs, project context, and state-machine files.
Writes must go through a runtime API or command outbox, not arbitrary browser
file edits.

Current repository state has two layers:

- Host-visible state already present in this repo: `agents/lead_engineer/tasks`,
  `BACKLOG-BOARD.md`, `STATUS.md`, `reviews`, `agents/project`, and release
  evidence.
- Runtime-template state created by installed projects: `agents/messages`,
  `agents/runtime/sessions`, `agents/runtime/events`, `agents/runtime/claims`,
  and stop files, driven by template scripts under
  `src/agent_runtime/templates/project/scripts`.

## Normalized View Records

### Task

Canonical fields:

- `id`: task frontmatter `id` or filename stem.
- `status`: task frontmatter `status`.
- `priority`: task frontmatter `priority`.
- `owner_agent`: task frontmatter `owner`.
- `tags`: task frontmatter `tags`.
- `description`: task body under `## Goal` / scope sections.
- `created_at`: task frontmatter `created` when present.
- `audit_log`: task frontmatter `audit_log`.

Derived fields:

- `title`: filename slug or first goal sentence.
- `lane`: mapped from status for Kanban: `planned -> Backlog`,
  `ready -> Ready`, `in_progress -> In Progress`, `blocked/hold -> Blocked`,
  `review -> Review`, `completed/done -> Done`.
- `order`: generated board order for MVP; later persist as `order` or rank field.
- `summary`: first sentence from `## Goal`.
- `team`: derived using board/team mapping.
- `value`, `score`, `difficulty_label`: derived by `backlog_board.py`.
- `related_messages`, `related_events`, `related_reviews`: derived by task id search.

Initial JSON shape:

```json
{
  "id": "TASK-AR-226",
  "title": "UI Runtime Data Map",
  "status": "completed",
  "lane": "Done",
  "priority": "P0",
  "order": 0,
  "owner_agent": "lead-engineer",
  "team": "agent-runtime-core",
  "labels": ["ui-console", "data-map", "runtime-state"],
  "description": "...",
  "blocked_reason": null,
  "created_at": "2026-06-10",
  "updated_at": null,
  "completed_at": null,
  "audit_log": ["AGENT_RUNTIME_UI_CONSOLE_BRIEF.md", "BACKLOG.md"]
}
```

### Agent

Canonical fields:

- `id`: session `agent_id`, or role id when no session exists.
- `role`: session `role` or `roles.yml` id.
- `status`: session status plus event-derived state.
- `current_task_id`: session `task_id` or latest claimed message `task_id`.
- `provider` and `model`: worker event fields when available.

Derived fields:

- `display_name`: role id converted to label.
- `online`: true when session status is `spawning` or `active`, or latest event
  is recent enough.
- `last_heartbeat`: latest event `ts` for that role.
- `last_message`: latest message touching role.
- `error_state`: latest unresolved `provider_error` event.

### Message

Canonical fields:

- `id`, `from`, `to`, `task_id`, `intent`, `type`, `status`, `ts`,
  `in_reply_to`, `evidence`, `next` from message frontmatter.
- body content from the markdown body.

Derived fields:

- `channel`: `task:<task_id>` if task-bound, otherwise `role:<to>`.
- `thread_root_id`: first non-empty `in_reply_to` chain root.
- `created_at`: alias of `ts`.
- `answered_at`: timestamp of reply/status event when available.

### Event

Canonical fields:

- JSONL record from `agents/runtime/events/*.jsonl`.
- Required minimum: `ts`, `role`, `event`.
- Event-specific ids: `message_id`, `reply_id`, `task_id`, `pipeline`.

Derived fields:

- `id`: `<event-file>:<line-number>` for stable local display.
- `type`: alias of `event`.
- `actor`: `role`.
- `created_at`: `ts`.
- `severity`: `error` when event name or payload indicates provider/gate error,
  otherwise `info`.

### Goal

Canonical fields:

- Current durable source is incomplete. `STATUS.md` contains current cycle and
  handoff state, but not a standalone goal record.
- Active thread goal may exist outside repo state in the Codex runtime.

Derived MVP fields:

- `id`: `current-thread-goal` or `STATUS:<heading>` until runtime goal JSON exists.
- `title`: first objective line from `STATUS.md` / active goal summary.
- `status`: mapped from cycle machine: `intake/planned/executing/review/done`.
- `updated_at`: latest `STATUS.md` update or file mtime.

Required follow-up gap for `TASK-AR-227`:

- Add `GET /api/goals` returning an explicit gap when no durable goal record
  exists.
- Do not invent a persistent goal database in the UI layer.

## Safe Write Strategy

### Allowed in MVP Read-Only Phase

- Read task files and generated board.
- Read message, session, and event files when present.
- Read `STATUS.md`, `agents/project`, review/evidence files, and state machines.
- Poll every 2-5 seconds and show source freshness per panel.

### Safe Write-Through in Later CRUD Phase

Use a runtime API first when available:

- `POST /api/tasks`
- `PATCH /api/tasks/:id`
- `POST /api/tasks/:id/reorder`
- `POST /api/messages`
- `POST /api/commands`

Fallback when no API exists:

- Write exactly one command JSON file under `.ui_outbox/`.
- Runtime validates and applies the command.
- UI waits for task/event/message state to reflect the result.

Command examples:

```json
{
  "id": "COMMAND-20260610-120000-a1b2c3",
  "type": "task.update",
  "target": "TASK-AR-226",
  "payload": {
    "status": "in_progress"
  },
  "created_by": "ui",
  "created_at": "2026-06-10T12:00:00+09:00"
}
```

```json
{
  "id": "COMMAND-20260610-120100-a1b2c3",
  "type": "message.send",
  "target": "lead-engineer",
  "payload": {
    "task_id": "TASK-AR-227",
    "instruction": "Implement the read-only UI adapter contract."
  },
  "created_by": "ui",
  "created_at": "2026-06-10T12:01:00+09:00"
}
```

Forbidden direct mutations:

- Browser editing `agents/runtime/claims/*.claim`.
- Browser setting message `claimed` or `answered`.
- Browser appending worker events directly.
- Browser touching stop files except through runtime API/outbox.
- Browser rewriting generated views or derived JSON indexes.

## Ordering Semantics

Current board order is generated by `scripts/backlog_board.py` using lane, score,
and task id. That is good enough for read-only UI and first Kanban display, but
not enough for drag-and-drop reorder because the generated order is not itself
canonical.

Initial rule:

- The read-only UI displays generated order from `BACKLOG-BOARD.md` or the
  adapter's board renderer.
- CRUD reorder must not rewrite `BACKLOG-BOARD.md`.
- `TASK-AR-229` must introduce either a canonical `order` field in task
  frontmatter or a small runtime-owned ordering file.
- Until that exists, drag-and-drop reorder should emit a command request and
  show `pending_runtime_support`.

## Adapter Contract For TASK-AR-227

`TASK-AR-227` should expose one read-first adapter surface:

```text
GET /api/state
GET /api/tasks
GET /api/tasks/:id
GET /api/agents
GET /api/messages
GET /api/events
GET /api/goals
GET /api/sources
```

Minimum `/api/state` response:

```json
{
  "generated_at": "2026-06-10T00:00:00+09:00",
  "sources": [
    {
      "id": "tasks",
      "path": "agents/lead_engineer/tasks/TASK-*.md",
      "fresh": true,
      "last_read_at": "2026-06-10T00:00:00+09:00",
      "mutation_boundary": "api_or_outbox"
    }
  ],
  "tasks": [],
  "agents": [],
  "messages": [],
  "events": [],
  "goals": [],
  "gaps": []
}
```

Required parser behavior:

- Missing optional directories return empty arrays plus source gap records.
- Malformed records return source warnings, not a crashed UI.
- Every normalized record includes `source_path` and `source_kind`.
- Derived fields are marked or documented as derived.
- Adapter must not write files for read endpoints.
