## Blocking Findings

### 1. Identifier-shaped provider, endpoint, prompt, exception, role, correlation, and event-ID values still cross the event boundary

The remediation correctly gives state, result-state, attention-kind, and
attention-state fields Runtime-owned allowlists. It also removes URI punctuation
from `_SAFE_IDENTIFIER` and rejects a finite set of token prefixes and exact
sensitive segments.

Other caller-controlled fields still use the generic `_identifier()` policy
(`src/agent_runtime/allimbot.py:197-222`, `src/agent_runtime/allimbot.py:285-286`).
Roles add only a kebab-case shape check
(`src/agent_runtime/allimbot.py:236-240`), and correlations reuse the same
generic filter (`src/agent_runtime/allimbot.py:355-363`). Returned event IDs
also reuse it (`src/agent_runtime/allimbot.py:408-412`).

An import-sentinel probe first confirmed that the exact prior fixtures now fail
before optional import:

```text
sk-proj-SYNTHETIC-CREDENTIAL-123 -> rejected; calls=[]
https://events.invalid/destination -> rejected; calls=[]
provider-slack -> rejected; calls=[]
prompt-secret -> rejected; calls=[]
exception-secret -> rejected; calls=[]
URL/token correlations -> rejected; calls=[]
```

The same probe then used compact, display-safe forms that do not contain one of
the finite forbidden segments:

```text
task_id=127.0.0.1                    -> spooled; import/load/construct/emit
task_id=events.invalid               -> spooled; import/load/construct/emit
gate=discord                         -> spooled; import/load/construct/emit
gate=ignorepreviousinstructions      -> spooled; import/load/construct/emit
gate=databaseconnectionfailed        -> spooled; import/load/construct/emit
owner_role=discord                   -> spooled; import/load/construct/emit
session_id=events.invalid            -> spooled; import/load/construct/emit
turn_id=discord                      -> spooled; import/load/construct/emit
dedupe_key=ignorepreviousinstructions -> spooled; import/load/construct/emit
```

Those values reach the fake emitter; data-field values also enter Runtime's
rendered summary. `discord` is an unlisted provider name,
`events.invalid`/`127.0.0.1` are destination-shaped hosts, and the compact
prompt/exception forms demonstrate that separator-based segment matching is
not a semantic boundary. An arbitrary provider-shaped role passes the
"field-specific" role check because that check establishes syntax, not a
Runtime-owned role vocabulary or trusted derivation.

The returned-ID check has the same gap:

```text
returned sk-proj-SYNTHETIC-CREDENTIAL-123 -> unavailable:invalid_event_id
returned https://events.invalid           -> unavailable:invalid_event_id
returned discord                          -> spooled; event_id=discord
returned ignorepreviousinstructions       -> spooled; event_id preserved
```

This still violates the task's requirement that caller-controlled prompt,
exception, credential, endpoint, provider, and destination values cannot cross
the boundary, including correlations and returned IDs. A blacklist cannot
prove that negative property.

Required rework:

1. replace generic identifier handling with positive, field-specific formats
   for task IDs, releases, gates, correlations, and Allimbot event IDs;
2. resolve `owner_role` through a Runtime-owned canonical role registry or use
   only trusted Runtime-derived values;
3. validate returned Allimbot IDs against the actual Allimbot ID contract,
   rather than the same caller-facing generic identifier;
4. add failure-first tests for provider names not present in a local blacklist,
   hostname/IP destinations, compact prompt/exception strings, arbitrary
   canonical role slugs, correlations, and returned IDs, with import/emitter
   sentinels.

### 2. A substituted unit specification can still erase the registered footprint

The remediation correctly unions explicit `--target-file` values with the
targets parsed from the supplied `--unit-spec`
(`scripts/task_claim_dispatcher.py:373-376`). `analyze_unit()` also unions that
supplied specification with the snapshot
(`src/agent_runtime/security_service.py:411-449`).

Neither seam binds the supplied path and frontmatter to `--task-id` and
`--unit-id`, however. The dispatcher only checks that the string is non-empty
before invoking the gate (`scripts/task_claim_dispatcher.py:693-719`), and the
security analyzer does not validate `task_id`, `unit_id`, or a canonical
registered-unit location.

Independent dispatcher probe:

```text
requested task_id=TASK-PROBE
requested unit_id=UNIT-TASK-PROBE-001
canonical registered unit target=.env.production
supplied unit_spec=reviews/safe-substitute-unit.md
substitute target=README.md

dispatcher_substitute_rc=0
dispatcher_substitute_claims=1
persisted target_files=["README.md"]
persisted unit_spec=reviews/safe-substitute-unit.md
```

The installed real security gate passed and the dispatcher persisted the claim.
The canonical `.env.production` target was never classified. Active-claim
rechecks subsequently trust the same substituted path, so they do not repair
the bypass.

This defeats both "requires a registered unit specification" and "registered
targets cannot be narrowed." The explicit-snapshot fixture is fixed, but the
same footprint can be narrowed by changing which document is treated as the
registered specification.

Required rework:

1. resolve the canonical unit specification from `task_id` and `unit_id`, or
   strictly validate the supplied path against that canonical location;
2. validate unit frontmatter identity against the requested task/unit before
   security analysis and before claim persistence;
3. reject absolute, out-of-tree, review, missing, mismatched, or duplicate unit
   specification paths at both dispatcher and active-claim seams;
4. add a regression proving a safe substitute cannot hide a risky canonical
   registered target.

### 3. Existing non-file configuration fails open, and an explicit empty risk-path list fails closed

Ordinary missing, malformed-file, and unsafe-path cases now have the intended
behavior:

```text
missing agent_runtime.yml        -> pass as empty host overlay
malformed risk_paths scalar      -> SecurityPolicyError
unsafe ../production risk path   -> SecurityPolicyError
malformed-file dispatcher seam   -> refused before claim persistence
```

`_host_risk_paths()` first calls `Path.is_file()` and returns an empty tuple
when it is false (`src/agent_runtime/security_service.py:217-226`). This
collapses a missing path and an existing non-file path into the same fail-open
state.

Independent policy and dispatcher probes created a directory named
`agent_runtime.yml`:

```text
policy analyze_unit status=pass
dispatcher returncode=0
persisted claims=1
```

The existing unreadable configuration surface was therefore treated as if no
configuration existed. The low-risk unit targeted
`services/prod/client.py`, exactly the sort of host-defined production surface
that disappears when `host.risk_paths` cannot be loaded.

The first W4b also required a valid empty list to remain valid, and W4a/docs
claim that behavior. A syntactically valid YAML flow list does not work with
the bounded parser:

```text
host:
  risk_paths: []

result=SecurityPolicyError("host risk-path configuration is unavailable or malformed")
```

Omitting the field works, but the documented explicit empty-list state does
not. This is conservative rather than a bypass, yet it means the prior finding
is not fully disposed as claimed.

Required rework:

1. treat an existing non-regular, dangling, unreadable, or otherwise
   unparseable `agent_runtime.yml` as a bounded policy error;
2. distinguish absence using a path-existence check that does not collapse
   non-file surfaces into "missing";
3. support the documented explicit empty list, or make the canonical
   representation and tests unambiguous;
4. add policy and dispatcher regressions for directory/symlink config paths and
   an explicit empty list.
