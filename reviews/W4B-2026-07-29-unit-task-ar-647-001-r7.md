## Blocking Finding

### A non-rendered HTML-block line satisfies `Security Controls`

The section scanner removes an HTML comment and then runs its heading regular
expression against the remainder of the same physical line:

```python
if in_html_comment:
    comment_end = visible.find("-->")
    ...
    visible = visible[comment_end + 3 :]
    in_html_comment = False
...
heading = re.match(r"^##\s+(.+?)\s*$", visible)
```

That transformation does not match CommonMark block parsing. A physical line
that terminates an HTML comment block remains part of the HTML block; text
following `-->` on that line is not reparsed as a Markdown heading.

The independent temporary-host dispatcher probe used:

```text
target_files:
  - .env.production
risk_tier: high
security_sensitive: true
approval_required: true
escalation_triggers:
  - security
---

<!--
hidden comment
-->## Security Controls
```

The local CommonMark parser emitted one `html_block` token and no `h2` token.
The Runtime section scanner nevertheless returned `security controls`.

Observed claim boundary:

```text
dispatcher_returncode=0
persisted_claims=1
policy_error=false
```

The same fail-open result occurred for:

```text
<!-- hidden comment -->## Security Controls

<script>
## Security Controls
</script>

<pre>
## Security Controls
</pre>
```

By contrast, the registered ordinary forms remained blocked:

````text
<!--
## Security Controls
-->

```text
## Security Controls
```
````

Those two passing regressions do not cover the HTML-block state transition
that permits claim persistence.

This is material because `Security Controls` is a mandatory pre-claim
requirement for the `secrets` and `auth` risk classes. The false section
positive occurs before persistence at the exact guardrail introduced by this
unit.
