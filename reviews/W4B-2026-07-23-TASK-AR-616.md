## Post-W4b Adjudication

**MAINTAIN APPROVE** at exact HEAD
`b52ab3d6208d27e355896011691b8367dfa60e23`.

The skeptic's initial whitespace finding does not block TASK-AR-616. The
registered plan and task require the existing classifier to remain unchanged,
and byte comparison proves that it did. TASK-AR-615 had already made
whitespace-only stdout part of the accepted logically-empty normalization and
recorded that choice as residual risk. Requiring byte-empty stdout or replacing
the stderr normalization in this task would therefore change, rather than
enforce, the registered acceptance contract.

The duplicate-commit probe is technically useful but does not establish an
actual Git outcome. It executes a successful real commit and then replaces the
child result with a fabricated rc 128, whitespace stdout, and the recognized
pre-commit diagnostic. Tightening stdout to byte-empty would not make that
threat model safe: the same wrapper could fabricate empty stdout and the same
duplicate would result.

Git 2.54.0 source, matching the failing hosted runner version, places normal
HEAD resolution at the start of `git commit`, then creates the commit object
with `commit_tree_extended()`, and only afterward advances HEAD through
`update_head_with_reflog()`. Its internal sequencer likewise calls
`parse_head()` before its tree/commit write and ref update. The exact
`could not parse HEAD` path is therefore pre-mutation in the reviewed Git
execution paths. Post-ref-update failures use other diagnostics, and the
post-commit hook cannot affect the outcome of `git commit`.

Primary references:

- <https://github.com/git/git/blob/v2.54.0/builtin/commit.c#L1813-L1819>
- <https://github.com/git/git/blob/v2.54.0/builtin/commit.c#L1938-L1967>
- <https://github.com/git/git/blob/v2.54.0/sequencer.c#L1497-L1517>
- <https://github.com/git/git/blob/v2.54.0/sequencer.c#L1685-L1697>
- <https://git-scm.com/docs/githooks#_post_commit>

Accordingly, the fabricated post-success result is an adversarial wrapper
case outside this fresh-fixture direct-Git contract. It remains a worthwhile
defense-in-depth scenario, not an in-scope acceptance failure or a reason to
reverse the verified verdict.

The proposed state guard is sufficient for that defense-in-depth scenario
without changing the approved classifier: snapshot the resolved HEAD object ID
immediately before each commit attempt, and after any recognized-shaped
failure retry only if the resolved state is available and unchanged. A changed
HEAD must stop loudly without another commit call. An unborn HEAD needs an
explicit sentinel, and any pre- or post-snapshot failure must fail closed. This
catches the skeptic's real-commit-then-forged-result sequence, including an
unborn-to-created transition; focused tests should cover unchanged, changed,
unborn-to-created, and snapshot-unavailable cases. It is optional hardening for
a separately registered change. If added to the reviewed implementation, its
new behavior and tests require fresh W4a and independent W4b verification.
