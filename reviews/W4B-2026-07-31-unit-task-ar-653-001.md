## P1-1 — A forged before-count is accepted as verified reduction

`record_cleanup()` reads the projection's top-level `hot_count` and uses it as
the trusted cleanup baseline
(`src/agent_runtime/state_projection.py:1633-1640`). It checks only that this
value is an integer and that the current value is smaller. Although the
receipt carries `before_sources`, `_cleanup_outcome()` never validates those
source bindings or proves that `before_hot_count` agrees with their counts
(`src/agent_runtime/state_projection.py:1111-1141`). The baseline plan is
likewise accepted when its alleged digest merely has 64 hexadecimal
characters (`src/agent_runtime/state_projection.py:1641-1650`).

### Independent public-API reproduction

In an isolated temporary repository, the public projection/receipt flow was
used with a current source containing 11 hot items:

1. write a normal projection;
2. alter only top-level `hot_count` from 11 to 16, leaving
   `sources[0].hot_count=11` and the current source digest unchanged; and
3. call `record_cleanup()` with an existing task-shaped authorization.

Observed result:

```text
outcome=verified_reduction
readiness=ready
before_hot_count=16
before_source_hot_count=11
resulting_hot_count=11
```

No source item was removed. The forged scalar converted the unchanged source
into a verified reduction and released the overdue obligation.

### Required repair

- Reject a baseline unless its complete source schema, paths, presence,
  digests, and hot counts are valid and its top-level hot count is recomputed
  from those sources.
- Bind the receipt to a recomputed canonical baseline projection/plan digest,
  not a caller-editable scalar or a digest-shaped string.
- Replay the same before-source and plan validation in `_cleanup_outcome()`;
  validating only the receipt's self-digest is insufficient.
- Add regression cases for mismatched top-level/per-source counts, altered
  before-source digests, and a fabricated cleanup-plan digest.

## P1-2 — Filename shape is treated as cleanup authority

`_safe_existing_ref()` establishes only repository containment, file
existence, and filename/path shape
(`src/agent_runtime/state_projection.py:1045-1080`). A task authorization is
accepted solely because it is a Markdown file under
`agents/lead_engineer/tasks/` whose name begins with `TASK-` or `UNIT-TASK-`.
An owner decision is accepted solely because it also has such a task shape or
because a file under `reviews/` begins with
`REVIEW-`, `AUDIT-`, `RETRO-`, or `DECISION-`. Neither path validates the
task/unit, approving owner/role, cleanup scope, source binding, or an explicit
no-touch decision.

### Independent public-API reproduction

An isolated overdue repository containing 16 hot items was given:

- `agents/lead_engineer/tasks/TASK-SCRIBE.md`, containing only an unrelated
  heading; and
- `reviews/REVIEW-UNRELATED.md`, containing only unrelated prose and no owner
  or no-touch decision.

Passing those two files to `record_cleanup()` without reducing the source
produced:

```text
outcome=owner_decision
readiness=ready_with_owner_decision
closure_blocking=False
source_debt=overdue
```

The source debt remains visible, but a non-authoritative unrelated document
unblocks closure. This violates the documented authority boundary.

### Required repair

- Define and validate a canonical authorization/decision schema or
  frontmatter. It must bind the current task/unit, source/cleanup scope and
  relevant digests, decision type, approver identity, and an authorized owner
  role.
- Require an explicit no-touch decision; do not infer authority or intent
  from directory, filename prefix, or mere existence.
- Add regressions proving that unrelated task-shaped files and unrelated
  `REVIEW-*` records are rejected and cannot yield
  `ready_with_owner_decision`.
