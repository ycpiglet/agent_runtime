# TASK-AR-652 final W4b governance scope amendment

## Bottom Line

The fresh independent W4b recheck verified the four previously reported P1
repairs, then found two remaining economic-integrity defects and one exact-
candidate governance failure. The first two remain inside the registered
Runtime routing and receipt footprint. The governance failure is caused solely
by the seven-day rolling throughput projection changing as time passes while
`taskset_work_gate.py` masks the other wall-clock projections.

This amendment adds only the gate, its packaged mirror and regression test, the
generated board, and the managed-host lock to the active footprint. No commit
or claim release occurred before this amendment. The board was regenerated by
the orchestrator after the failure was reproduced; the change remains
uncommitted and reviewable in this claimed worktree.

## Decision

- Treat pre-resolved tier/provider dictionaries as assertions at the final
  prompt and message boundary; independently derive executable authority from
  role, requested tier, explicit registered triggers, and provider.
- Require observed reasoning for every comparable route unless the receipt's
  authoritative route schema explicitly records reasoning as `unsupported`.
- Add `scripts/taskset_work_gate.py`,
  `src/agent_runtime/templates/project/scripts/taskset_work_gate.py`, and
  `tests/test_taskset_work_gate.py` to close the time-only throughput drift.
- Add `BACKLOG-BOARD.md` so the serial projection owner can publish the current
  rolling value after the deterministic gate repair.
- Add `tests/fixtures/host/agent_runtime.lock.json` because the packaged gate is
  a managed template asset.
- Re-record the taskset T3 assumptions with this review as the design record
  before commit or another W4 verification attempt.

## Invariants

- Task status, priority, taskset identity, product scope, provider credentials,
  and external systems remain unchanged.
- The board gate continues to detect task additions, task status changes,
  active-claim changes, and all other record-derived drift.
- Time-derived `generated_at`, WIP age, attention decay, and rolling throughput
  remain visible in the board but cannot make an unchanged record set stale.
- No live provider, credential, account, package, consumer primary, database,
  broker, notification, deploy, push, tag, version, publication, or release is
  authorized.

## Verification Boundary

- Forged high/raw route assertions fail before prompt or message emission.
- Missing native baseline reasoning produces no token or monetary eligibility.
- Root and packaged taskset gates accept throughput-only time drift and still
  reject record-derived drift.
- Owner governance must pass on the exact clean candidate before a fresh W4b.
