## Reproduced Blockers

### F1 — active claims do not validate canonical task/unit lifecycle state

`scripts/state_sync_gate.py::_validate_active_claim` validates the claim's
identity, task/unit ownership, claim refs, worktree/branch, and pointer
records. It never rejects a worker claim when its canonical task or unit is
done, nor when dispatch has not been projected from `planned`/`worker_ready`
to an active lifecycle status.

An isolated temporary fixture using the repository's state-sync test helpers
produced these exact results:

```text
completed-task-with-open-sibling: []
completed-unit: []
planned-task-unit: []
worker_ready-task-unit: []
```

Each `[]` is the complete list of block findings. The first fixture includes a
second `in_progress` task in the same taskset, proving this is not masked by
the existing `taskset:active-but-complete` check.

This violates the unit's acceptance requirement that impossible active and
completed combinations block, and its requirement that task/unit lifecycle
projections correlate with an active worker claim.

### F2 — linked-checkout resolution rejects valid relative worker worktrees

`scripts/state_sync_gate.py::_worktree` resolves a relative claim path only
against the gate's current root. Protocol claims emitted by
`task_claim_dispatcher.py` default to `.worktrees/<TASK-ID>`, which is relative
to the primary checkout. When the gate runs from a linked worker worktree,
that path is incorrectly interpreted below the linked checkout.

An isolated primary repository plus linked reviewer checkout recorded a valid
relative worker worktree and produced:

```text
linked-checkout-relative-worktree-blocks=['claim:invalid-worktree:CLAIM-TEST-001']
```

`scripts/parallel_worktree_gate.py::_resolved_worktree` already implements the
required primary-root fallback through `_git_primary_root`; the state-sync
gate must follow the same resolution contract before it evaluates main-checkout
or branch integrity.

## Required Repair Scope

1. In root and template `state_sync_gate.py`, block every active non-overlay
   worker claim whose canonical task or unit is a done status, and block claims
   whose canonical task/unit remain pre-dispatch (`planned` or `worker_ready`)
   rather than active/review lifecycle states. Add explicit regression tests
   for all four scenarios, including an open sibling taskset case.
2. Resolve relative worker `worktree_path` values against the primary checkout
   when they are absent below the linked checkout, matching
   `parallel_worktree_gate._resolved_worktree`. Add a linked-checkout test for
   a `.worktrees/TASK-*` claim path, then recheck branch and main-checkout
   integrity through that resolved path.
3. Preserve the existing strict literal-overlay rule (`overlay is True`),
   additive primary-pointer semantics for parallel workers, TASK-AR-631's
   explicit recovery watch, work-schema zero-warning result, host lock, and
   root/template shared-gate parity.
