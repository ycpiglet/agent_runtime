## Security and Code Review

- `_URL_USERINFO_RE` recognizes scheme-qualified URL userinfo and replaces the
  complete user/password segment before the host with `[REDACTED]`.
- `_SENSITIVE_ASSIGNMENT_RE` is case-insensitive and covers `password`,
  `passwd`, `token`, `access_token`, `access-token`, `secret`, and
  `authorization` assignments using either `:` or `=`.
- The same sanitizer is applied independently to every command argument,
  stdout, and stderr before any value enters the assertion text.
- The helper renders its own sanitized command rather than trusting
  `CompletedProcess.args`, so the reported command corresponds to the actual
  helper input and passes through the redaction boundary.
- Diagnostic fields are constructed in a fixed sequence: summary, command,
  return code, stdout, then stderr. Empty streams use the deterministic
  `<empty>` marker.
- On success, subprocess still receives the same command, cwd, merged
  environment, output capture, UTF-8 decoding, and replacement error handling.
  Switching from `check=True` to explicit return-code handling changes only the
  failure exception and message contract.

## Residual Risk and Scope

- Redaction recognizes URL userinfo and labeled sensitive assignments. An
  arbitrary unlabeled secret fragment cannot be identified reliably; helper
  callers must continue to avoid passing credentials outside supported URL or
  key/value forms. Environment contents are not included in diagnostics.
- The sensitive-assignment rule redacts the remainder of its line. This is
  intentionally conservative for secrecy but may remove non-sensitive context
  following a credential on the same line.
- Diagnostics are not size-limited. Very large Git stdout/stderr would produce
  a large assertion, although this helper operates only in focused local tests.
- This verifier changed no helper code, production code, tests, claim, release
  state, or shared index.
