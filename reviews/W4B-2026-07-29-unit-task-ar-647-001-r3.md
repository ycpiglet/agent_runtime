## Blocking Findings

### 1. A malformed role registry can still authorize arbitrary caller-controlled roles

The new event boundary correctly resolves non-system roles through
`agents/project/ORG-MODEL.yml`, rejects a symlinked registry, and rejects the
second-W4b value `owner_role=discord` when it is not registered.

However, `_registered_owner_roles()` is a permissive line scanner. It records
every line matching two spaces plus `- id: <role>` while ignoring unsupported
or malformed surrounding structure. It does not prove that the file is a
valid instance of the Runtime registry shape.

Two independent import-sentinel probes reproduced the bypass:

```yaml
schema: agent-runtime-org-model/v1
roles:
  - id: lead-engineer
this is not yaml
```

```text
result=spooled
calls=load,construct,emit
```

More importantly, an invalid nested structure can introduce the exact
provider-shaped value that the positive contract was intended to exclude:

```yaml
schema: agent-runtime-org-model/v1
roles:
  child:
  - id: discord
```

```text
owner_role=discord
result=spooled
calls=load,construct,emit
```

This is not a registry-derived authorization. Under YAML structure the
`discord` line is not a direct item of the `roles` sequence, and the document
is outside the managed registry contract. The scanner nevertheless treats it
as trusted and renders it into the summary/data sent to the emitter.

Required rework:

1. fail closed on every unsupported indentation, duplicate top-level section,
   malformed scalar/list shape, or incomplete role entry in the bounded
   `ORG-MODEL.yml` contract;
2. collect role IDs only from structurally valid direct `roles` entries;
3. preserve the existing regular-file and symlink-component checks; and
4. add import-sentinel regressions for trailing garbage, nested `- id`,
   duplicate `roles` sections, malformed/empty registries, and symlinked
   registries.

### 2. A symlinked parent directory can substitute the installed security gate

The remediation correctly refuses a directory, direct symlink, or dangling
symlink at `scripts/security_service_gate.py`. The dispatcher checks
`gate.is_symlink()` and `gate.is_file()`, but those checks follow symlinks in
parent components.

The independent probe created:

```text
<host>/scripts -> <host>/external-scripts
<host>/external-scripts/security_service_gate.py = raise SystemExit(0)
canonical unit target = .env.production
canonical unit security metadata = deficient
```

The final path itself reports `is_symlink() == false` because only its parent
is a symlink. The substituted no-op gate ran and the dispatcher persisted the
claim:

```text
dispatcher_returncode=0
scripts_is_symlink=true
gate_is_symlink=false
persisted_claims=1
persisted_target_files=[".env.production"]
```

This bypasses the pre-persistence security-service boundary completely.

Required rework:

1. resolve the installed gate through an `lstat()` walk from the host root;
2. require `scripts/` to be a real directory and the final gate to be a
   regular, non-symlink managed file;
3. fail closed on inaccessible or concurrently invalidated path components;
4. keep root/template dispatcher mirrors byte-identical; and
5. add a dispatcher regression proving a symlinked parent cannot hide a risky
   canonical target behind a no-op gate.
