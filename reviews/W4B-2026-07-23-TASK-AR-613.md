## Blocking Finding

### [P1] A successful metric masks an exhausted sibling query and release-auto proceeds

At exact HEAD `86f425c4`, the end of
`scripts/release_cadence_trigger.py::build_report` performs this conditional
promotion:

```python
if _QUERY_ERRORS:
    base["git_query_errors"] = list(_QUERY_ERRORS)
    if not triggered:
        base["status"] = "error"
        base["reason"] = "git-query-error"
```

The error is promoted only when no other metric triggered. That makes a
partially evaluated trigger look more trustworthy when one surviving metric
happens to cross a threshold.

The auditor exported `86f425c4`, created a real `v0.2.0` repository with 40
post-tag commits, and made only this query return 128 three times:

```text
git log --format=%s v0.2.0..HEAD
```

All other Git calls used the real executable. The exact result was:

```text
HEAD86_PARTIAL_CALLS=3
STATUS=watch
TRIGGERED=True
COMMITS=40
ERRORS=1
REASON=None
BUMP=patch
```

The structured error itself was correctly sanitized, but the report treated it
as non-fatal. Injecting that exact cadence module into the real release-auto
orchestrator then produced:

```text
HEAD86_RELEASE_AUTO_PARTIAL_RESULT=executed
NEW_FAILURE_CALLS=3
MUTATED=False
HAS_ERRORS=False
TARGET=v0.2.1
```

`mutated=False` is only because the independent probe used the default dry-run.
The `executed` route demonstrates that the trigger error was dropped and the
orchestrator passed the release decision boundary. With explicit execution and
otherwise passing gates, this fail-open can authorize state mutation from
incomplete cadence data.

Required rework:

1. Treat any `_QUERY_ERRORS` remaining after report construction as an
   unevaluated cadence: set status error, `triggered=false`, clear the finding
   and release recommendation, and set reason `git-query-error` regardless of
   other successful metrics.
2. Add a failure-first partial-query regression where baseline and commit count
   succeed, the subject/log query exhausts three retries, and another metric
   would otherwise trigger.
3. Exercise the same partial report through release-auto and require
   `trigger-error`, nonzero trigger-error exit semantics, no decision artifacts,
   and no mutation. As defense in depth, release-auto should reject cadence
   status/reason/errors before relying on `triggered`.
4. Resolve or explicitly route the shared self-eval consumer behavior described
   below; changing cadence `build_report()` alone does not affect a consumer
   that calls the shared `_git` helper directly.

### No-Tag, Sanitation, And Retry-Provenance Matrix

The known `fatal: No names found, cannot describe anything.` response at rc
128 with empty stdout was classified in one call. A terminal newline on that
known stderr is normalized, and whitespace-only stdout is treated as logically
empty. Wrong rc 1, any non-whitespace stdout, an unknown no-tag-like message,
or a known message followed by a second fatal diagnostic each made three calls
and returned `error/git-query-error`. Thus conflicting evidence cannot be
accepted as a quiet repository; localized or unfamiliar Git output fails
closed.

The direct sanitizer probe combined Bearer and Basic authorization values,
quoted whitespace, `password`, `passwd`, `token`, `access_token`,
`access-token`, `secret`, `authorization`, two URL-userinfo credentials, an
OSError, and credential-bearing command arguments. None of the 12 sentinel
secrets survived. The mixed retry sequence preserved `attempts=3`, reset the
stale rc 7 to null when OSError became the final failure kind, and sanitized
both `command` and `error`.
