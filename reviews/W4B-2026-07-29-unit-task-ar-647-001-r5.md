## Blocking Findings

### 1. A selected security-service profile fails open when its gate is stably absent

The dispatcher now validates a present gate's parent path, file type, stable
snapshot, and exact managed digest. It also executes the validated source
snapshot instead of reopening the path. Those are meaningful improvements.

However, `_security_service_refusal()` still treats a stably absent final gate
as proof that the host is core-only. It does not consult the host's profile
selection or another non-bypassable installation marker.

The independent temporary-host probe used:

```text
agent_runtime.yml:
  schema: agent-runtime-config/v2
  profiles: [core, security-service]

managed .allimbot.json: present
managed SECURITY-SERVICE-POLICY.json: present
scripts/: real directory
scripts/security_service_gate.py: absent
canonical unit target: .env.production
required security metadata/sections: absent
```

Result:

```text
selected_security_profile=true
managed_policy_present=true
managed_recipe_present=true
gate_present=false
dispatcher_returncode=0
persisted_claims=1
```

The doctor already classifies this same selected-profile state as a
`missing-gate` blocker. Claim dispatch nevertheless bypasses the gate and
persists the risky claim. This means deleting one managed profile asset is
enough to disable the pre-persistence security boundary.

Required rework:

1. distinguish a genuinely core-only host from a host that selected
   `security-service` and lost its gate;
2. when the profile is selected, treat an absent, unreadable, non-regular,
   symlinked, drifted, or concurrently invalidated gate as a claim blocker;
3. preserve the intended core-only behavior when the profile is not selected;
   and
4. add a dispatcher regression proving a selected profile with a missing gate
   persists zero claims for a deficient canonical risky unit.

### 2. An unsupported quoted scalar still authorizes an arbitrary role

The bounded parser rejects all seven registered malformed fixtures and
collects role IDs only from complete direct `roles` entries. It nevertheless
uses `_org_scalar()` for `updated_at` and `display_name`, and that scalar
grammar accepts YAML quote indicators without parsing or rejecting them.

The independent probe supplied:

```yaml
schema: agent-runtime-org-model/v1
updated_at: "
tiers: [planner]
teams:
  - id: engineering
    display_name: Engineering
roles:
  - id: discord
    tier: planner
    team: engineering
    aliases: []
```

The document has an unterminated quoted scalar. A YAML parser rejects it with
`ScannerError`, while the Runtime parser returned `{"discord"}`. An
import-sentinel event probe then produced:

```text
result=spooled
calls=load,construct,emit(owner_role=discord)
```

This is the same authorization class as the third W4b finding: the whole
registry is not a valid supported document, but a direct role from it becomes
trusted event data.

Required rework:

1. define and enforce a fixed plain-scalar grammar for every scalar field, or
   otherwise reject unsupported YAML quote/tag/anchor/block-scalar syntax;
2. validate `updated_at` and display-name values under that grammar before
   returning any role IDs;
3. retain the bounded stable-file and component `lstat()` protections; and
4. add an import-sentinel regression for the unterminated-quote fixture and
   adjacent unsupported scalar indicators.

This does not require adding a YAML dependency; a fail-closed fixed subset is
sufficient.
