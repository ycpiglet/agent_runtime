## P1-1 - Role policy is not bound to the execution surfaces

`scripts/model_routing.py:113-182` defines the expected explicit role matrix,
and `resolve_subagent_tier()` denies an unauthorized high request when that
helper is called. The actual worker surfaces do not consistently call it:

- `agent_worker._message_routing_decision()` and
  `auto_dispatch._routing_decision_for_item()` return `None` for a Scribe that
  has no explicit `routing_model`, so the Scribe low-cost policy is not applied.
- Both functions accept a Scribe `routing_model=opus` as a manual override
  without any registered escalation reason.
- `codex_subagent_bridge.create_dispatch_packet()` validates against
  `subagent_dispatch`'s six-role registry, which does not contain `scribe`, so
  the native bridge cannot execute the Scribe policy at all.

Bounded reproduction:

```text
{"agent_worker_role_decision": null,
 "auto_dispatch_role_decision": null,
 "codex_bridge_scribe": "KeyError: \"unknown subagent role 'scribe'. Known: explorer, implementer, reviewer, auditor, strategist, skeptic\""}
{"agent_worker_selected": "opus",
 "auto_dispatch_selected": "opus",
 "registered_escalation_reason_present": false}
```

Required repair: make role policy resolution mandatory at every worker/native
entry point, include every declared role family in the executable registry,
and reject or down-route unauthorized high-tier overrides before provider
configuration is applied.

## P1-2 - Durable budget preflight is neither authoritative nor atomic

Claim creation stores `task_token_budget` and `claim_token_budget` in the claim
and projection (`scripts/task_claim_dispatcher.py:581-609,757-758,1845-1850`),
but no execution surface loads those values from a claim. `agent_worker` reads
only message frontmatter, `auto_dispatch` reads only the item/context, and the
single Codex bridge reads only optional CLI arguments. The council bridge has
no task budget, claim budget, claim ID, or dispatch-ceiling parameters and
therefore cannot enforce even a configured zero budget.

In addition, `eval_harness.budget_preflight()` reads usage without holding the
append lock and creates no durable reservation. The lock is taken only later
while appending the completion receipt. Two processes can therefore both pass
preflight before either calls the provider or records usage. A native bridge
packet has the same time-of-check/time-of-use gap because its preflight occurs
when the packet is created, while the parent session performs the provider
spawn later without a locked recheck.

Offline concurrent reproductions:

```text
task budget 100, two dispatch ceilings 60:
{"preflight_allowed": [true, true],
 "provider_calls": ["race-0", "race-1"],
 "receipt_count": 2,
 "recorded_tokens": 120,
 "configured_task_budget": 100}

same dispatch ID in two concurrent runners:
{"preflight_allowed": [true, true],
 "provider_call_count": 2,
 "receipt_count": 1,
 "receipt_recorded_flags": [true, false]}

council zero-budget surface:
{"has_task_token_budget": false,
 "has_claim_token_budget": false,
 "has_dispatch_ceiling": false,
 "zero_budget_call": "TypeError: create_council_packet() got an unexpected keyword argument 'task_token_budget'"}
```

The second result proves that duplicate receipt rejection after the call does
not prevent duplicate provider side effects. Required repair: resolve budgets
from the authoritative task/claim record, propagate them automatically to all
surfaces including every council member, and atomically reserve each dispatch
ceiling before exposing executable spawn/provider arguments. Completion,
failure, or cancellation must settle that reservation.

## P1-3 - Exactly-one receipts and ledger fail-closed integrity have bypasses

Receipt append itself is locked and duplicate appends are rejected, but the
end-to-end invariant is incomplete:

- `agent_worker.process_one()` returns after losing a claimed message at the
  pre-process claim check (`agent_worker.py:810-813`) without writing a skipped
  receipt.
- Single and council Codex deterministic-complete paths return before creating
  a packet or receipt (`codex_subagent_bridge.py:302-314,675-688`). Unresolved
  deterministic preflight raises without a receipt as well.
- Council receipts are created only by the post-execution `record_council()`
  command and are always marked `completed`; there is no member error/skip
  record path. A failed native spawn can simply have no receipt.
- The shipped `verify_sdk_backend.py:36-62` remains a direct live
  `provider.run()` path with no durable budget preflight or receipt.
- `_strict_records()` validates JSON/object shape but not schema uniqueness or
  duplicate dispatch/receipt IDs. A ledger already containing duplicate IDs is
  accepted for an unrelated new dispatch instead of being rejected as
  untrusted.

Offline reproductions:

```text
agent_worker lost-claim path:
{"processed": true, "provider_calls": 0, "receipt_count": 0,
 "receipt_path_exists": false}

bridge deterministic completion:
{"single_status": "deterministic_complete_no_spawn",
 "council_status": "deterministic_complete_no_spawn",
 "receipt_count": 0, "packet_dir_exists": false}

pre-existing duplicate-ID ledger, new dispatch:
{"exception": null,
 "result": {"allowed": true, "reason": "within_budget",
            "task_tokens_used": 20}}
```

Required repair: enumerate completion, provider error, policy/budget skip,
claim loss, deterministic completion, native spawn failure, and every council
member as terminal states that must settle exactly one immutable dispatch
record. Validate the entire ledger schema and global ID uniqueness under the
same lock before any preflight is allowed.

## P1-4 - A caller assertion is accepted as an observed comparable baseline

Savings eligibility checks the string
`baseline_observation_status == "observed"`, but that value and the baseline
model, tokens, billed cost, and currency are copied directly from message/item
metadata. There is no baseline receipt ID, digest, source, or lookup proving a
separate observed execution. Consequently request metadata can elevate a
configured baseline into observed economic evidence. The compatibility
`record_outcome` rows are even exempt from the baseline-observation-status
check in `eval_harness.py:571-587`.

An offline fake provider produced one actual receipt and no baseline receipt.
Supplying only the item metadata status made both token and monetary savings
eligible:

```text
{"receipt_count_total": 1,
 "baseline_receipt_count": 0,
 "caller_supplied_baseline_status": "observed",
 "token_eligible_records": 1,
 "saved_tokens": 80,
 "monetary_verified": true,
 "saved_billed_cost_usd": 0.08}
```

The same-currency comparison and real route-change checks work as local
predicates, but they cannot make an unproven baseline observed. Required
repair: require a referenced immutable baseline receipt (including observed
model/reasoning, usage, billed cost, currency, comparable workload identity,
and provenance), resolve it from the ledger, and exclude legacy/unreferenced
rows from economic savings totals.
